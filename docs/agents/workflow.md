# Рабочий процесс и границы действий

Область: Git, жизненный цикл MR и безопасность действующего экземпляра.
Этот документ обязателен перед любой работой; технические соглашения здесь не дублируются.

## Работающая сеть

- Приложение постоянно обслуживает сеть пользователя и обеспечивает связь с агентом.
  Подготовка правок не разрешает перезапускать демон/sing-box, переключать VPN,
  переприменять маршруты либо менять DNS, NM и polkit.
- Не выполнять автоматически `make dev`, `make daemon`, `make desktop`, `make stop`,
  `make restart`, `make sync`, recover/reset-host и изменяющие состояние вызовы API.
  Для конкретного воздействия нужно явное разрешение; уже данное не спрашивать повторно.
- Checkout запущенного приложения защищён: не менять в нём исходники (Vite/HMR),
  ветку, зависимости, бинарники или пользовательские данные ради разработки.
  Прочитать `git config --get vpnrouter.developmentRoot` и работать в указанной dev-копии.
  Подготовка описана в [DEVELOPMENT.md](../DEVELOPMENT.md).
- Сборки и тесты не запускают второй маршрутизатор и не заменяют рабочий sidecar,
  `bin/`, PID-файлы или содержимое `~/.config/vpn-router/`. Другие `--data`/`--listen`
  сами по себе не изолируют маршруты, TUN и DNS. Безопасные команды — в [quality.md](quality.md).
- Не считать любой GET безопасным: список подписок может сохранять исправленный выбор узла.
  Для диагностики проверять реализацию обработчика; не раскрывать секреты из настроек/логов.

## Один цикл разработки — одна фичевая ветка

1. Основная ветка — `main`. Проверить текущую ветку и dirty state; сохранить пользовательские правки.
2. Пока текущая `feature/*` ещё не слита, все следующие доработки вести в ней.
   Новая задача и новый коммит не являются причиной создавать ещё одну ветку.
3. После подтверждённого merge сначала fetch и актуализация `main` до `origin/main`
   в dev-репозитории, только fast-forward. Проверить, что изменения MR входят в main.
   Папку работающего приложения автоматически не переключать и не обновлять через pull.
4. После каждого слияния **обязательно переиндексировать main через GitNexus**,
   даже если MR менял только документы/правила. Проверить совпадение индекса с HEAD main
   по [gitnexus.md](gitnexus.md). Нельзя переносить индекс фичевой ветки как индекс main.
5. Удалить завершённую локальную и remote-ветку, если они ещё существуют и все изменения
   сохранены в main. Не удалять незакоммиченные изменения и занятые/чужие рабочие копии.
   Не использовать reset --hard, force push и принудительное удаление пользовательских файлов.
6. Зачеркнуть выполненные пункты на их местах в плане и обновить интерактивный отчёт
   по [documentation.md](documentation.md).
7. Для следующего цикла создать **одну** новую `feature/<task>` от актуального main.
   До её слияния продолжать все согласованные доработки в ней.

## Авторизация и завершение

- Commit, push и merge — по явному поручению пользователя в рамках задачи.
  Ранее согласованный порядок передачи правок через Git сохраняется между сообщениями.
- Минимальный diff: не менять несвязанный код. OpenSpec — только по явному запросу.
- Перед завершением выполнить [quality.md](quality.md), проверить diff и сохранность
  работающего экземпляра. Сообщить результат, проверки и реальные ограничения.
- После исправления дать короткие шаги ручной проверки. Для применения использовать
  обычный `make dev` в рабочей папке: перезапуск выполняет пользователь.
